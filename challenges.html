Freedom from content language bondage

The three-dimensional web is not a new dream. In 1994, the Web3D Consortium introduced the Virtual Reality Markup Language to help realize that vision. However, VRML and X3D (its XML-based successor) failed to achieve widespread use. No doubt many factors explain why.

I submit that one key reason was their choice to model 3-D scenes using a content, rather than procedural language.

Content languages are good at capturing a situation’s symbolic state, hierarchically specifying its parts and attributes. These traits are a decent fit for detailing a 3-D scene and its component meshes.

However, static languages do a poor job of capturing a scene’s dynamic behavior. This becomes apparent when rendering and exploring a typical VRML/X3D scene. At best, one sees little motion and is given few ways to interact with the content. When such scenes look dull and offer little to do, one becomes quickly bored and eager to move on.

Procedural languages, on the other hand, are very good at managing complex behaviors, such as motion and collision physics, artificially intelligent agents and sophisticated user interaction scenarios. Such languages also enable the procedural generation of 3-D content, thereby improving a scene’s variety, performance and storage requirements.

In fairness, the X3D language does offer a way to incorporate procedural behavior: one may include Javascript code within the X3D scene. Such scripts would manipulate the scene’s content and attributes and handle user interactions, making possible scenes that are more sophisticated and engaging.

Yet, few X3D scenes take advantage of this procedural scripting, as this capability is more of an awkward afterthought than an integral part of the modeling language: One must now learn two language grammars, X3D and Javascript. One must create monolithic script code that has little modular synergy with the content. And one cannot find good libraries that ease the creation of complex behaviors.

The history of the two-dimensional web illustrates the unfortunate consequences of having separate languages for content and behavior.

In the beginning, the web was invented to make it easier for academics to share documents around the world. The HTML content language provided a simple, straightforward way to describe such static documents.

However, as companies started building interactive web-sites for e-mail, e-commerce, social media and more, HTML (as a content language) became insufficient. Procedural technologies such as Flash, OLE and Javascript were increasingly employed, ultimately leading to the creation of progressively more complex architectures to marry HTML content with Javascript behavior. Ajax and jQuery were invented to responsively modify a page’s content. Server-side frameworks were used to procedurally generate content on the fly, injecting procedural capabilities awkwardly within HTML (e.g., Handlebars or AngularJS). Extensive Javascript libraries were built to make it easier to transform dull static content into attractive, immersive, and interactive web sites.

Today, the boundary between a web site’s content and behavior is complex and blurred. The site’s content and capability is spread out across multiple languages and technologies. Interactive websites are hard to build and harder to maintain. No small portion of this complexity is because web sites cannot be built using a single language and modular architecture that seamlessly manages both its dynamic state and interactive behavior.

Dynamic, attractive and interactive content are far more important to making 3-D scenes “sticky” than they are for two-dimensional websites. Thus, if we want to ensure the widespread growth of an open three-dimensional web, we are better off building 3-D worlds using a single language that marries together, in a familiar and modular way, the elegant strengths of both content and procedural languages.
